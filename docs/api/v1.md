# Partner API v1

Base path: `/api/v1`. Provider directory reads allow 60 requests/minute by IP. Availability and booking status require `X-API-Key`; production keys are stored only as comma-separated SHA-256 fingerprints in `PARTNER_API_KEYS_SHA256` and allow 300 requests/minute per key.

- `GET /providers?city=&category=` — public provider/listing metadata; no contact data.
- `GET /availability?providerId=` — occurrence capacity and availability.
- `GET /bookings?reference=` — lifecycle status without buyer PII.
- `POST /affiliate/click` with `{ "partner": "...", "listingId": "..." }` — records signed attribution only when the listing is transactable.

Responses include `version: "v1"`. Breaking changes require a new base path; v1 fields may only be added, not removed or retyped.

## Booking webhooks

Set `PARTNER_WEBHOOK_URL` and `PARTNER_WEBHOOK_SECRET`. Events are `booking.pending`, `booking.confirmed`, and the remaining booking-state names. The JSON envelope includes `id`, `type`, `apiVersion`, `createdAt`, and PII-minimised `data`.

Each request includes:

- `X-Yoga-Webhook-Id`
- `X-Yoga-Webhook-Timestamp`
- `X-Yoga-Webhook-Signature: v1=<hex HMAC-SHA256>`

Verify the signature over `<timestamp>.<raw request body>`, reject stale timestamps, and deduplicate on the webhook ID. Non-2xx deliveries use exponential backoff. Production must persist the outbox in the regional database; the in-memory repository adapter is for local/demo use.
